## フェーズ2 — 顧客向け予約・認証・データ運用

- [ ] Mini App予約画面: 起動経路別の実機で空き枠閲覧・受付・取消・期限切れ・エラーを確認。Kumoで狭幅・キーボード操作・表示設定を検証。
- [ ] initData: サーバーHMAC/公式第三者署名、auth_date、Bot一致、リプレイ対策、顧客専用セッション。改ざん・期限切れ・別Botを拒否するテストが通る。
- [ ] Telegram Login: 現行OIDCを主方式、従来Widgetを互換要件がある場合だけ採用。署名・issuer/audience/expiry・state/nonce・PKCE・許可URLを検証し、認証成功だけで同意を追加しない。
- [ ] 本人紐付け: 検証済みIDと確認済み連絡先で明示統合。名前／usernameだけでは統合せず、別人・競合・Bot変更のテストが通る。
- [ ] 連絡先・同意UI: 目的・運営主体・媒体・文面版を提示し、本人の許可・撤回・訂正と証跡を表示。確認メール／OTPは承認済み経路のみ。管理者による誤確認の訂正手順を用意。
- [ ] 台帳運用: 顧客検索・詳細、流入履歴、担当・タグ、重複処理、データ保持期限、アクセス監査・削除／匿名化。目的別の最小権限テストが通る。
- [ ] バックアップ／復元: 暗号化・非公開保存・鍵管理・期限・復元ツールを実装し、隔離DBへ件数・関係・同意撤回まで一致する復元演習が通る。
- [ ] 大規模エクスポート: 子履歴を含むページング／ストリーミング、スナップショット整合性、実測上限・タイムアウト・中断再開を検証。
- [ ] 予約業務: 担当／部屋重複、枠変更、取消期限、仮押さえTTL、タイムゾーン・夏時間、同時受付を仕様化し、競合・再起動・期限切れのテストが通る。
- [ ] 通知: 同意・媒体・Botごとの権限・承認境界を確認し、予約確認・リマインド・取消を冪等ジョブ化。停止・429・応答不明時に無条件再送しないテストが通る。
- [ ] 再連絡運用: 利用不能経路を停止、同意と確認状態を再照合、文面・宛先を承認、新Botの本人開始後に権限を記録。自動切替・制限回避なし。
- [ ] API/MCP同等性: 新機能の全操作を認可付きMCPツールで提供し、UI・API・MCPで同じ認可・状態遷移テストが通る。

## フェーズ3 — Stars決済（導入審査後）

- [ ] 導入審査: 商品区分、対象国、禁止業種、規約、購入条件、取消・返金・問い合わせ体制を運営者が承認。必要な外部審査の結果と未確定事項を記録。
- [ ] 注文・請求: XTR整数・注文ID・顧客・Bot・予約仮押さえを結び、改ざん金額・通貨・別顧客・重複請求を拒否。
- [ ] pre_checkout: 事前承認したルールで在庫・期限・金額を照合し10秒内に応答。処理遅延／障害は安全に拒否。人の投稿承認キューと混同しない。
- [ ] 入金・予約確定: successful_paymentのみを正とし、bot+charge IDで重複防止。順序逆転・再送・処理落ち・枠喪失の回復テストが通る。
- [ ] 返金: refundStarPayment相当の実行前承認・状態照合・監査・再試行を実装。予約取消だけで返金済みにしない。
- [ ] サポート: 購入条件、/paysupport等、問い合わせ先、履行・返金履歴を顧客と担当者が確認できる。
- [ ] 決済UI/MCP: 注文・支払・返金・審査状態をKumoとMCPで同じ権限付きで操作できる。
- [ ] テスト環境: オフラインfixture後、明示承認されたTelegram専用テスト環境で購入・キャンセル・返金を検証。証跡と責任者確認後にのみ本番可否判断。
